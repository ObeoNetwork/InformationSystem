h1(#database_and_scaffolding). ISD - Base de données et Scaffolding

h2(#database_and_scaffolding_overview). Présentation

Le _Scaffolding_ est une technique popularisée par le socle de développement _Ruby on Rails_ qui vise à produire des livrables (code, modèle, documentation) à partir des informations structurelles d'une base de données.
En l’occurrence, l'outillage de scaffolding d'IS Designer propose les fonctionnalités suivantes :

* un module capable d'extraire les informations structurelles d'une base de données relationnelle existante (MySQL, MariaDB, Oracle, PostgreSQL, SQL Server ou H2) et de produire un modèle _Database_,
* un modeleur de base de données, basé sur Sirius, permettant de réaliser des modèles physiques et logiques de données (MPD et MLD),
* un module de comparaison de modèles _Database_ et des générateurs de scripts SQL et de fichiers _ChangeLog_ pour Liquibase permettant de mettre à jour la base de données,
* un ensemble de transformations permettant d'automatiser la conversion et de maintenir la cohérence entre un modèle physique et un modèle logique, ainsi qu'entre un modèle logique et un modèle d'entités. Ces transformations sont bidirectionnelles (du modèle entité jusqu'au modèle physique et vice versa).

h3(#supported_databases). Bases de données supportées

Les types de bases de données suivants sont supportés :

|_. Base |_. Version |
| Oracle | 11g à 26ai |
| MySQL | 5 à 9.6 |
| MariaDB | 10.2 à 13.0.2 |
| H2 | 1.3 à 1.4.200 |
| PostgreSQL | 9.5 à 18.1 |
| SQL Server | 2008, 2022 et 2025 |

Le type natif UUID de MariaDB nécessite MariaDB 10.7 ou une version ultérieure. La bibliothèque de types MariaDB propose ce type sans contrôle de la version cible. Avant de créer une colonne UUID, directement dans un MPD ou par scaffolding depuis un MLD, vérifier que la base cible satisfait ce prérequis.

La rétrocompatibilité des drivers permet en théorie d'importer des schémas de base de versions antérieures à celles supportées, mais aucune garantie ne peut être donnée en ce sens.

h4(#database_uuid). Type UUID

Le type logique @UUID@ représente un identifiant de 128 bits. Sa longueur est fixe et ne se paramètre pas dans le MLD. La taille de sa représentation dans une base de données est déterminée lors de la transformation vers le MPD.

h5(#uuid_logical_to_physical). Transformation du MLD vers le MPD

Une colonne de type logique @UUID@ est convertie selon la base cible :

|_. Base cible |_. Type physique produit |
| Oracle | @VARCHAR2(40)@ |
| MySQL | @char(36)@ |
| MariaDB | @uuid@, à partir de MariaDB 10.7 |
| PostgreSQL | @UUID@ |
| SQL Server | @uniqueidentifier@ |
| H2 | @UUID@ |

Pour Oracle et MySQL, les longueurs 40 et 36 sont définies automatiquement par le scaffolding. Il n'est pas nécessaire de renseigner une longueur sur l'UUID logique.

h5(#uuid_physical_to_logical). Rétro-ingénierie et transformation du MPD vers le MLD

La rétro-ingénierie reconnaît les colonnes natives @UUID@ de H2 et PostgreSQL, @uuid@ de MariaDB et @uniqueidentifier@ de SQL Server dans le MPD importé. Lors de la transformation de ce MPD vers un MLD, ces types deviennent des colonnes de type logique @UUID@.

Les colonnes @char@ de MySQL et @VARCHAR2@ d'Oracle sont des colonnes textuelles. Leur transformation vers le MLD produit le type logique @Texte@, sans déduire automatiquement qu'elles contiennent des UUID.

h5(#uuid_entity_transformation). Transformation vers un modèle d'entités

Une colonne de type logique @UUID@ devient un attribut de type @String@ (texte) dans le modèle d'entités. Dans le sens inverse, un attribut @String@ est converti en type logique @Texte@, sans déduction automatique du type @UUID@.

Le choix du type @UUID@ ne génère pas automatiquement les valeurs des identifiants. Leur attribution doit être prévue par l'application ou par une configuration explicite de la base de données.

h2(#sql_and_liquibase). Comparaison et génération SQL et Liquibase

h3(#database_comparison). Comparaison et fusion

L'outillage de comparaison permet de comparer deux versions de MPD, soit de deux fichiers stockés localement, soit d'une version locale avec une version stockée dans un référentiel de type Subversion. L'outillage est basé sur EMF Compare et fournit une extension permettant d'améliorer la pertinence de la comparaison sur ce type particulier de modèle.
Pour comparer deux versions de MPD, sélectionner les deux fichiers à comparer et utiliser _Compare With > Each Other_ proposé dans le menu contextuel. Lors d'une comparaison de fichiers locaux (par opposition à la comparaison via l'outillage Subversion) EMF Compare considère les fichiers dans un ordre alphabétique. Idéalement, le nommage à adopter doit être tel que la version la plus récente du MPD se trouve en première position comme dans l'exemple ci-dessous :

!{max-width:100%}pics/database/ModelExplorer-CompareDatabaseModels.png!

L'option de menu _Compare with Each Other_ est également disponible dans la vue _History_ :

!pics/database/HistoryView-CompareModels.png!

En cas de problème lors de la comparaison d'une base de données ayant des liens vers des éléments externes stockés dans des fichiers différents, il est recommandé de lire la documentation sur la résolution de modèle logique utilisée par _EMF Compare_:

h3(#database_liquibase_generation). Génération de fichiers ChangeLog pour Liquibase

h4(#liquibase_update_changelog). Génération de ChangeLog de modification

Un fichier _ChangeLog_ pour Liquibase permet de passer d'une version d'une base de données à une suivante. Pour générer un tel fichier _ChangeLog_, la première étape est de comparer les deux modèles de bases de données en s'assurant que le plus récent soit en première position (cf. paragraphe précédent).

Une fois la comparaison effectuée, la génération du fichier _ChangeLog_ est rendue accessible par le bouton _Generate Liquibase_ présent dans la barre d'outils. Le fichier _ChangeLog_ généré permet la mise à jour du schéma correspondant au MPD le plus ancien :

!{max-width:100%}pics/database/DatabaseComparison-GenerateLiquibase.png!

S'il n'existe pas déjà, un répertoire @liquibase@ est créé à la racine du projet pour contenir l'ensemble des scripts. Ce répertoire est structuré de la manière suivante :

* @liquibase/<Type BDD>/<Nom BDD>/<Date>/run.changelog.xml@
* @liquibase/<Type BDD>/<Nom BDD>/run.changelog.xml@
* @liquibase/<Type BDD>/<Nom BDD>/liquibase.properties@

Les deux fichiers @run.changelog.xml@ générés sont identiques, l'un est généré sous un répertoire daté permettant de conserver un historique. L'autre permet d'utiliser plus facilement les commandes _Liquibase_ étant donné qu'il est référencé par le fichier @liquibase.properties@.

Contrairement au fichier @run.changelog.xml@, le fichier @liquibase.properties@ n'est pas écrasé à chaque génération, il est initialisé seulement s'il n'existe pas.

h4(#liquibase_creation_changelog). Génération de ChangeLog de création

Un _ChangeLog_ de création permet de générer la structure complète d’une base de données. La génération d’un tel _ChangeLog_ est disponible dans le menu contextuel du modèle _Database_, sous l’entrée _IS Designer > Generate Liquibase Changelog_ :

!pics/database/DatabaseMenu-GenerateLiquibaseChangelog.png!

Une fenêtre propose ensuite une option de création des schémas s'ils n'existent pas :

!pics/database/LiquibaseGenerationDialog-CreateSchemas.png!
Cette option n'a aucun impact sur les bases de données Oracle pour lesquelles un schéma est nécessairement associé à un utilisateur.
Cette option n'est prise en compte que lors de l'ajout d'un nouveau schéma, toute modification (suppression ou renommage de schéma) n'est pas gérée.

h4(#liquibase_global_changelog). Génération d’un ChangeLog global

Un _ChangeLog_ global permet de regrouper plusieurs générations pour appliquer leurs modifications dans l’ordre chronologique. Il référence les fichiers historiques par des instructions Liquibase @include@, sans recopier leurs _changeSet_.

Pour le créer, sélectionner le dossier @liquibase/<Type BDD>/<Nom BDD>@ dans l’explorateur, puis utiliser le menu contextuel _Liquibase > Create global changelog_. La sélection doit porter sur un seul dossier.

Le dialogue présente les fichiers @run.changelog.xml@ des sous-dossiers datés, du plus ancien au plus récent :

!pics/database/GlobalChangelogDialog-GenerationSelection.png!

Une sélection discontinue est autorisée. Un avertissement non bloquant signale que des générations intermédiaires sont exclues. La cohérence de l’enchaînement des modifications reste à vérifier par l’utilisateur.

Cliquer sur _Finish_ pour créer @liquibase/<Type BDD>/<Nom BDD>/global_run.changelog.xml@. Les inclusions sont ordonnées chronologiquement et leurs chemins sont relatifs à ce fichier. Si un changelog global existe déjà, il est remplacé par celui correspondant à la nouvelle sélection.

La génération est bloquée si plusieurs _changeSet_ des historiques sélectionnés portent le même identifiant.

h4(#liquibase_apply_changelog). Application d’un ChangeLog

Pour appliquer un _ChangeLog_ sur une base de données, sélectionner son fichier dans l’explorateur puis utiliser le menu contextuel _Liquibase > Apply changelog_.

!pics/database/LiquibaseMenu-ApplyChangelog.png!

Le dialogue _Apply Changelog — Database Connection_ permet de choisir la connexion à utiliser. À chaque ouverture, les champs _URL_, _Username_ et _Password_ sont initialisés avec les propriétés @url@, @username@ et @password@ du fichier @liquibase/<Type BDD>/<Nom BDD>/liquibase.properties@.

!pics/database/ApplyChangelogDialog-DatabaseConnection.png!

Les connexions enregistrées sont définies dans le fichier @credentials.properties@, situé à côté de @liquibase.properties@. Si ce fichier n’existe pas, il est créé automatiquement à l’ouverture du dialogue, avec comme premier triplet @url.1@, @username.1@ et @password.1@ les valeurs de @liquibase.properties@.

Pour ajouter une connexion, compléter un triplet avec le même numéro pour les trois propriétés. Exemple à adapter aux bases utilisées :

bc. url.1=jdbc:postgresql://localhost:5432/ebookstore
username.1=john
password.1=123
#url.2=jdbc:postgresql://localhost:5432/ebookstore_test
#username.2=johny
#password.2=123

L’ordre des triplets est libre, et leurs numéros peuvent être discontinus.

Choisir une entrée dans la liste _URL_ renseigne l’URL, l’utilisateur et le mot de passe associés. Les champs restent modifiables. Les modifications saisies dans le dialogue ne sont pas enregistrées dans les fichiers de propriétés.

h2(#database_transformations). Transformations

Dans IS Designer, le scaffolding permet de transformer les modèles entre les niveaux entités, modèle logique de données (MLD) et modèle physique de données (MPD), dans les deux sens.

Les transformations suivantes sont proposées afin d'initialiser un modèle à partir d'un autre :

* transformation d'un MPD en MLD,
* transformation d'un MLD en modèle d'entités,
* transformation d'un modèle d'entités en MLD,
* transformation d'un MLD en MPD.

Le mode opératoire est le même pour chacune des transformations.

h3(#database_transformation_source_and_target). Transformation depuis les modèles source et cible

Pour lancer une transformation, le modèle cible doit exister. Par exemple, pour une transformation d'un MPD en MLD, la première étape est la création d'un MLD vide.

La sélection doit porter sur un objet source et un objet cible, en dépliant les modèles dans la vue _Model Explorer_. Si la sélection porte sur les fichiers, le traitement ne pourra pas être lancé.

Pour un MPD ou un MLD, les objets source ou cible doivent être des _Data Base_ ou des _Schema_.
Pour un modèle d'entités, les objets source ou cible doivent être des _Entities_ ou des _Namespace_.

* Le menu contextuel _ISD > Scaffolding_ permet de sélectionner le type de transformation à effectuer. Seules les transformations possibles en fonction des objets sélectionnés sont activées :

!{max-width:100%}pics/database/ModelExplorer-ScaffoldingTransformations.png!

* La sélection d'une entrée de menu déclenche l'ouverture d'un assistant de sélection des ressources nécessaires à la résolution des dépendances externes. En effet, lors par exemple d'une transformation d'un MLD vers un MPD, il est possible que le MLD contienne des tables référençant des tables d'un autre MLD. Dans ce cas, le MPD externe en question doit être référencé afin que les clés étrangères soient résolues correctement :

!{max-width:100%}pics/database/ScaffoldingWizard-AdditionalResources.png!

Une fois le traitement exécuté, un message de confirmation s'affiche. Un modèle contenant les informations de scaffolding est créé dans le répertoire @scaffold@. Ce modèle peut être utilisé pour lancer un nouveau traitement de scaffolding sur les mêmes éléments.

h3(#database_transformation_scaffolding). Transformation depuis un modèle de scaffolding

La transformation peut être lancée directement depuis un modèle de scaffolding par :

* sélectionner le modèle dans le _Model Explorer_,
* lancer l'action du menu contextuel _ISD > Scaffolding_.

Les transformations disponibles dans le menu dépendent des objets source et cible utilisés par le modèle de scaffolding.
Une entrée de menu permet d'ajouter des ressources pour résoudre les dépendances externes comme lorsque l'assistant est utilisé (cf. paragraphe précédent).

À noter que lorsqu'une transformation est lancée en sélectionnant des objets source et cible pour lesquels un modèle de scaffolding existe déjà, il est proposé d'utiliser le modèle existant ou d'en créer un nouveau.

h3(#database_transformations_parameters). Paramétrage de la transformation d'un modèle d'entités en MLD

Dans le cas d'une transformation d'un modèle d'entités en MLD, deux colonnes techniques sont créées pour chaque table créée.
Ces colonnes sont :

* Une colonne de validité nommée avec le nom du schéma suffixé par @_XTOPSUP@
* Une colonne de date de mise à jour nommée avec le nom du schéma suffixé par @_XDMAJ@

La génération de ces colonnes peut être désactivée en ajoutant une métadonnée sur l'entité ou l'un des _Namespace_ parents :

* @Clé : DISABLE_ADDITIONAL_FIELDS_KEY@
* @Valeur : true@

Ces deux colonnes ne seront alors pas créées pour l'entité en question, ou pour toutes les entités contenues par le _Namespace_ en question.

h3(#notes). Paramétrage et gestion des évolutions

Les équivalences entre les types logiques et physiques, etc., ainsi que les règles de nommage sont paramétrables.

Aussi, dans le cas où une version du modèle cible existe déjà, il est conseillé d'effectuer la transformation vers un nouveau modèle puis d'utiliser l'outillage de comparaison et fusion afin de gérer l’incrémentalité des modifications. Voici un exemple illustrant ce scénario :

* l'équipe de développement fait évoluer le modèle d'entités et le livre à l'équipe DBA,
* l'équipe DBA peut ainsi lancer une transformation du modèle d'entités vers un nouveau MLD V2,
* l'équipe DBA peut ensuite comparer et fusionner le MLD V1 (incluant des modifications ajoutées préalablement par l'équipe DBA) et le MLD V2,
* l'équipe DBA peut ensuite effectuer une transformation du MLD V2 fusionné vers un MPD Oracle par exemple. Elle peut ensuite demander la comparaison et la génération du script SQL par rapport à une version plus ancienne du MPD.
